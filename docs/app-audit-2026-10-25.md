# Tablet Comics 0.4.2 — feature and functionality audit

Audited 25 October 2026. Package `dev.tabletcomics`, version code 8, minimum Android API 26, target API 35.

**Assessment:** the core reader exists, but tablet reliability and polish are not established. The highest priorities are RAR memory limits, archive cancellation/performance, and gesture lifecycle tests. The earlier successful builds and ten navigation tests do not establish that the reported page flash or tablet crashes are resolved.

This audit reviewed all application Kotlin sources, manifest, dependencies, tests, and the project guide. Production code and the released APK were not changed. Findings below distinguish source-confirmed behavior from device observations that could not be reproduced here.

## Prioritized findings

### F1 — High: RAR decompression memory is not limited to tablet capacity

`RarArchiveReader` constructs `Archive(staged)` without `ArchiveOptions`. The actual installed Junrar binary reports `DEFAULT_MAX_DICTIONARY_SIZE = 4294967296` bytes (4 GiB). This is an allowance, not an allocation for every comic; the requested dictionary depends on the archive. Nevertheless, an accepted archive can demand much more memory than an Android app heap allows. The reader's roughly 40 MiB bitmap budget does not govern that dictionary, compressed-page byte arrays, `ByteArrayOutputStream` copies, covers, or GPU resources.

**Impact:** large-dictionary CBR files can cause severe memory pressure during covers or reading. This is a confirmed configuration risk, not a confirmed explanation for the earlier MatePad crash. Set an explicit heap-aware extraction budget and report an understandable limit error before allocation.

Evidence: [RAR constructor](/workspace/app/src/main/java/dev/tabletcomics/archive/RarArchiveReader.kt:39), [bitmap budget](/workspace/app/src/main/java/dev/tabletcomics/reader/ComicReaderSession.kt:55), [engine results](/workspace/docs/audit-engine-results-2026-10-25.txt).

### F2 — High: a cover load can delay opening or switching comics

Generating a RAR cover calls `open(uri)`, copying the entire archive to private storage. Cover generation and reader opening share `archiveIoLock`. The copy loops do not check coroutine cancellation. If the user opens a comic while a large cover is being prepared, cancelling the library composition does not interrupt that synchronous copy; the reader waits for the same lock. Staging can also continue after leaving a loading comic. The 1 GiB free-space check runs on every 64 KiB copy chunk.

**Impact:** long waits that can feel like a frozen reader, especially with large CBRs or slow document providers. Add cancellable staging and extraction, prioritize active-reader work, and reuse staged copies where safe. Validate cancellation and lock release with delayed input streams.

Evidence: [shared preview lock](/workspace/app/src/main/java/dev/tabletcomics/MainActivity.kt:263), [RAR cover path](/workspace/app/src/main/java/dev/tabletcomics/archive/RarArchiveReader.kt:15), [RAR copy loop](/workspace/app/src/main/java/dev/tabletcomics/archive/RarArchiveReader.kt:27), [ZIP copy loop](/workspace/app/src/main/java/dev/tabletcomics/archive/ZipArchiveReader.kt:36).

### F3 — High for solid CBRs: prefetch and quality upgrades repeatedly replay extraction

The reader prepares a low-resolution current page, neighboring pages, then reads the current page again for its high-resolution version. On later turns, loading the next neighbor before upgrading the current page also moves extraction backwards. Junrar's solid-archive implementation resets and replays earlier entries when requesting an entry at or before its last extracted position. The app has no extracted-page disk cache.

**Impact:** a solid comic may repeatedly decompress much of the book during navigation, with worse delays near its end. This is confirmed from call order and engine implementation; no solid-archive timing measurement was performed. Cache extracted page content or use a sequential extraction policy for solid archives.

Evidence: [prefetch followed by reread](/workspace/app/src/main/java/dev/tabletcomics/reader/ComicReaderSession.kt:234), [RAR extraction call](/workspace/app/src/main/java/dev/tabletcomics/archive/RarArchiveReader.kt:59). Dependency source: `Archive.extractFile`, specifically `targetIdx <= lastProcessedFileIndex` and the replay loop.

### F4 — Medium: zero-offset gestures retain an old rendering snapshot

Starting a horizontal drag stores `turnFrame`. At a book boundary, or while a neighbor is unavailable, drag is set to zero. Releasing calls `settle`, which returns immediately when drag is zero without clearing `turnFrame`. Cancellation at zero also skips cleanup. A later full-resolution update keeps the same page index, so the reset effect does not run, and the canvas can continue drawing the older snapshot.

**Trigger:** swipe toward the unavailable previous page on the cover while its image is still upgrading, then release. **Impact:** a stale/soft page can remain displayed and old bitmaps stay referenced. Clear gesture snapshots on every exit, including zero-distance and cancelled gestures. This is a separate source-confirmed defect; it is not proven to be the user's brief wrong-page flash.

Evidence: [early return](/workspace/app/src/main/java/dev/tabletcomics/reader/PageTurnReader.kt:95), [snapshot capture](/workspace/app/src/main/java/dev/tabletcomics/reader/PageTurnReader.kt:144), [snapshot rendering](/workspace/app/src/main/java/dev/tabletcomics/reader/PageTurnReader.kt:160).

### F5 — Medium: seeking can repeatedly cancel work without showing loading

The slider calls `session.navigate()` on every movement, including repeated values that resolve to the same page/spread. Each call cancels the worker and starts another request. On a cache miss the old page remains visible, but the loading spinner is shown only when `session.current == null`. A neighboring-page decode error displays a central error surface whose only explicit action is leaving the book.

**Impact:** seeking can feel unresponsive; slow or damaged pages have weak recovery. Keep a separate slider drag value, seek on release or debounce, ignore duplicate targets, and show loading/error/retry state for the requested page.

Evidence: [slider](/workspace/app/src/main/java/dev/tabletcomics/MainActivity.kt:228), [worker cancellation](/workspace/app/src/main/java/dev/tabletcomics/reader/ComicReaderSession.kt:124), [loading and error UI](/workspace/app/src/main/java/dev/tabletcomics/MainActivity.kt:174).

### F6 — Medium: zoom can move the page out of view and does not load more detail

Pan is accumulated without bounds, while turning is disabled above approximately 1× zoom. There is no double-tap or explicit reset action. Zoom scales an existing bitmap; the current decode target is at most 1600 pixels on its longer side and is further rounded down by power-of-two sampling.

**Impact:** users can pan the comic entirely offscreen and must pinch back or navigate using controls to recover; small text becomes enlarged low-resolution pixels. Clamp pan to page bounds, offer reset/double-tap zoom, and load additional detail within a measured memory budget.

Evidence: [zoom/pan state](/workspace/app/src/main/java/dev/tabletcomics/reader/PageTurnReader.kt:74), [turn gating](/workspace/app/src/main/java/dev/tabletcomics/reader/PageTurnReader.kt:140), [decode sizing](/workspace/app/src/main/java/dev/tabletcomics/reader/ComicReaderSession.kt:57).

### F7 — Medium: active reading is not restored after activity/process recreation

The active book and session are held in ordinary Compose `remember` state. The activity ignores `savedInstanceState` for reader restoration. Orientation flags reduce recreation during rotation, but do not provide general lifecycle recovery. Progress itself is saved in preferences, so manually reopening the comic restores its saved page.

**Impact:** a system-driven recreation or process kill returns the user to the library. Save active-book identity and restore the session deliberately; verify rotation, background eviction, and process restoration on the tablet.

Evidence: [activity setup](/workspace/app/src/main/java/dev/tabletcomics/MainActivity.kt:59), [remembered state](/workspace/app/src/main/java/dev/tabletcomics/MainActivity.kt:71), [manifest handling](/workspace/app/src/main/AndroidManifest.xml:4).

### F8 — Medium: staged archives have no recovery cleanup policy

Archives are staged as `comic-*.zip` or `comic-*.rar` files and deleted on normal close/error handling. There is no startup cleanup, inactive-cache eviction, or ownership registry to recover files left by process death or a crash. The configured per-archive copy limit is 8 GiB.

**Impact:** interrupted sessions can leave large private files, consuming storage until Android or the user clears the cache. Add recovery cleanup for inactive app-owned files and enforce the guide's cache policy.

Evidence: [ZIP staging/deletion](/workspace/app/src/main/java/dev/tabletcomics/archive/ZipArchiveReader.kt:30), [RAR staging/deletion](/workspace/app/src/main/java/dev/tabletcomics/archive/RarArchiveReader.kt:21).

### F9 — Medium: library covers and contents can become inconsistent

ZIP cover generation selects the first suitable entry in physical archive order, whereas reading sorts entry paths naturally. A synthetic fixture with `10.png` before `2.png` demonstrates the difference: preview selection is `10.png`, reading starts at `2.png`. Cover cache keys contain only the URI; refreshing an archive changed in place does not invalidate its old cover. Folder scans are independently launched without cancelling older scans, so a slower old selection can overwrite results for a newer folder.

**Impact:** wrong covers, stale previews, and potentially a library that does not match the selected root. Use one indexed first-page rule, track file modification metadata, and cancel/token-check scans.

Evidence: [ZIP preview](/workspace/app/src/main/java/dev/tabletcomics/archive/ZipArchiveReader.kt:15), [reading order](/workspace/app/src/main/java/dev/tabletcomics/archive/ZipArchiveReader.kt:60), [cover cache](/workspace/app/src/main/java/dev/tabletcomics/MainActivity.kt:260), [scan jobs](/workspace/app/src/main/java/dev/tabletcomics/MainActivity.kt:90).

### F10 — Medium: format handling and recovery are narrower than the guide

The filename extension determines the reader; archive signatures are not checked before dispatch. A ZIP renamed to `.cbr` is sent to the RAR reader and fails. Single-file opening from the file manager/share sheet is not wired into the manifest. Password-protected archives are deferred, but only encrypted RAR entries receive an explicit tailored error; other engine failures can fall back to generic messages.

Evidence: [extension-based dispatch](/workspace/app/src/main/java/dev/tabletcomics/MainActivity.kt:248), [launch intents](/workspace/app/src/main/AndroidManifest.xml:5), [RAR encryption check](/workspace/app/src/main/java/dev/tabletcomics/archive/RarArchiveReader.kt:50).

## Additional scope and documentation gaps

- The library has no search, grid layout, selectable sorting, recent/continue-reading action, bookmarks or thumbnail navigation. Search/sorting/continue-reading were in the guide; bookmarks and thumbnail navigation are possible additions rather than prior must-haves.
- There is no Room database or file modification index; only URI-keyed preferences and an in-memory cover cache.
- Tap reveals controls; it does not implement page-edge tap navigation or double-tap zoom. Raw Canvas gestures have no equivalent accessible page actions.
- The reader does not keep the screen awake. This is a reader usability gap, not a previously specified requirement.
- Actual page-entry size limit is **24 MiB**, while README and guide say **100 MiB**. The implemented 8 GiB limit bounds the staged archive bytes, not total uncompressed content as described in the guide.
- The UnRAR notice exists in the source tree but is not packaged as an APK notice/About resource. The guide requests notices delivered with the app.
- The project is not currently a Git repository; there is no local commit history to correlate behavioral regressions with releases.

## Recommended repair and validation order

1. Bound RAR dictionary and total working memory; add delayed-input cancellation and cleanup checks. Verify large CBR opening and repeated book switches.
2. Improve solid-RAR extraction/caching and prioritize reader work over covers. Measure opening time, page latency and peak heap on the MatePad.
3. Fix gesture teardown and add Compose gesture/frame tests: fast repeated swipes, reversals, boundary gestures, release at zero, neighbor arrival, rotation and seek during settling. Verify all three animation styles and two-page spreads. The reported wrong-page flash remains unconfirmed until this is done.
4. Fix seeking feedback, zoom recovery, active-session restoration, and cache/cover invalidation.
5. Finish the tablet library and accessibility work, then validate actual HarmonyOS API compatibility and screenshot/video behavior on the intended device.

Passing compilation or the current ten unit tests alone is not sufficient evidence for a smooth, crash-free reader.
